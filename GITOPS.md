# GITOPS.md — expense-api GitOps pipeline (Week 6 Day 2)

## Repo split

`expense-project` (this repo) builds the app and pushes images.
`expense-config` (https://github.com/NishiS0205/expense-config) holds
only Kubernetes manifests, Kustomize overlays, and Argo CD
Application/AppProject/ApplicationSet definitions. Argo CD watches
`expense-config`, never `expense-project` directly.

## What's running

Argo CD `v3.3.12` (bumped from the curriculum's pinned `v2.11.7` — see
"Deviations from the reference" below), managing three Applications
generated by a single `ApplicationSet` matrix generator
(`expense-api-envs`): `expense-api-dev`, `expense-api-staging`,
`expense-api-prod`, one per Kustomize overlay, fanned out against the
one registered `in-cluster` destination (labelled
`uptimecrew.example.internal/tier: workload` so the matrix's `clusters`
generator picks it up).

## Deviations from the reference curriculum

1. **Argo CD version.** The reference pins `v2.11.7`. That version's
   comparison engine chokes on `.status.terminatingReplicas`, a
   Deployment status field introduced by a Kubernetes API version
   newer than what `v2.11.7` was built against — this k3d cluster runs
   `v1.35.5`. Upgraded to `v3.3.12` (current stable as of writing) to
   resolve `ComparisonError: field not declared in schema`.

2. **`Namespace` resource scope in the AppProject.** The reference
   lists `Namespace` under `namespaceResourceWhitelist`. Empirically,
   Argo CD `v3.3.12` still rejects it there with
   `resource :Namespace is not permitted in project 'expense'` —
   verified by direct testing, reproduced identically every time.
   `Namespace` is cluster-scoped per `kubectl api-resources`
   (`NAMESPACED=false`), and Argo CD's project validation checks scope
   against the live Kubernetes API, not against which list a doc
   happens to put it in. Fixed by moving `Namespace` into
   `clusterResourceWhitelist` instead, documented inline in
   `argocd/projects/expense.yaml`.

3. **`kubectl port-forward` to `argocd-server` was unreliable** on this
   Colima setup — reproducible "connection reset by peer" from the
   CNI network namespace on every attempt (delete-pod, full Colima
   restart, and pod-vs-Service forwarding targets all reproduced the
   identical failure; a bare `nc` connect succeeded while any real
   TLS/gRPC payload reset the connection, pointing to an MTU-class
   issue in Colima's virtual network stack). Routed around it
   entirely via an `nginx` Ingress + `/etc/hosts` entry
   (`argocd.local` → `127.0.0.1`, hitting the k3d load balancer's
   already-mapped host port `8080`) instead of `port-forward`.

## Environment differences (Kustomize overlay patches)

| | dev | staging | prod |
|---|---|---|---|
| Namespace | `expense-dev` | `expense-staging` | `expense-prod` |
| Replicas | 1 | 2 | 3 |
| `SPRING_PROFILES_ACTIVE` | dev | staging | prod |
| `LOG_LEVEL` | DEBUG | INFO | WARN |
| Ingress host | `expense.dev.uptimecrew.internal` | `expense.staging.uptimecrew.internal` | `expense.prod.uptimecrew.internal` |

The Ingress host had to be patched per-overlay — the base manifest
hardcodes the `dev` hostname, and nginx's admission webhook rejects
any second Ingress claiming a host that's already registered
elsewhere in the cluster. Discovered this the hard way: `staging` and
`prod` both failed to sync with
`host "expense.dev.uptimecrew.internal" ... is already defined in
ingress expense-dev/expense-api` until each overlay got its own
distinct host via a JSON6902 patch.

## Known gap: staging/prod have no working database

The base `ConfigMap` hardcodes datastore hostnames
(`postgres.expense-dev.svc.cluster.local`, etc.) that only resolve
inside the `expense-dev` namespace, where W5D3's throwaway
local-testing Postgres/Mongo pods happen to live. `expense-staging`
and `expense-prod` have no Postgres/Mongo of their own at all, so once
the app image actually pulls and starts, it crash-loops trying to
reach a database that was never provisioned for those namespaces.

This is deliberately left unresolved here — provisioning real,
per-environment datastores (or wiring per-env connection strings) is
infrastructure work well beyond what this GitOps exercise is testing.
The exercise's actual goal — proving Argo CD can read this Git repo,
render the correct per-env Kustomize overlay, and keep each
environment's declared resources in sync — is fully proven: all three
Applications reach `Synced`, `dev`'s pods reach `Running` against a
real pushed image, and the image-pull path (including the ECR
registry-name gotcha below) is confirmed working end-to-end.

## Other real bugs found and fixed along the way

- **Image `newName` needs the full ECR registry path.** Kustomize's
  `images:` transformer defaults to Docker Hub if `newName` is a bare
  repo name (`uptimecrew/expense-api`) rather than the fully-qualified
  ECR path. Every pod failed with `pull access denied` against
  `docker.io/uptimecrew/expense-api` until `newName` was corrected to
  `475790160484.dkr.ecr.us-east-1.amazonaws.com/uptimecrew/expense-api`
  in all three overlays.
- **k3d cluster nodes have no ECR credentials.** A local `docker
  login` only authenticates the host's Docker daemon, not the k3d
  node containers' own `containerd`. For this local-cluster exercise,
  resolved via `k3d image import` (loading the already-locally-built
  image directly into the cluster's nodes) rather than solving real
  node-level registry auth, since `imagePullPolicy: IfNotPresent` on
  the base Deployment means an already-present local image is never
  re-pulled from a registry.
- **Argo CD admin password mismatch after a fresh install.** The
  `argocd-secret`'s stored `admin.password` hash didn't correspond to
  what `argocd-initial-admin-secret` currently showed (likely from an
  earlier session predating this one). Reset via the documented
  `htpasswd -bnBC 10` + `kubectl patch secret argocd-secret` procedure
  rather than guessing.
